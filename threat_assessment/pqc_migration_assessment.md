# PQC Migration Assessment

## 1. Objective

This assessment maps quantum-vulnerable classical public-key cryptographic mechanisms to appropriate post-quantum replacements and evaluates the practical migration impact using the benchmark results generated by this project.

The assessment focuses on RSA-2048, ECDH P-256, and ECDSA P-256, with ML-KEM-768 and ML-DSA-65 evaluated as post-quantum alternatives.

---

## 2. Quantum Threat Mapping

| Classical mechanism | Cryptographic function | Quantum threat | PQC replacement |
|---|---|---|---|
| RSA-2048 | Public-key encryption / signatures | Shor's Algorithm | Function-dependent migration to ML-KEM and/or ML-DSA |
| ECDH P-256 | Key establishment | Shor's Algorithm | ML-KEM-768 |
| ECDSA P-256 | Digital signatures | Shor's Algorithm | ML-DSA-65 |

Shor's Algorithm threatens RSA and elliptic-curve cryptography because a sufficiently capable quantum computer could efficiently solve the underlying mathematical problems on which their security depends.

Grover's Algorithm primarily affects symmetric-key search security and is therefore treated separately from the public-key migration mappings above.

---

## 3. ECDH to ML-KEM Migration

### Classical mechanism

ECDH P-256 provides public-key key establishment based on the elliptic-curve discrete logarithm problem. This security assumption is vulnerable to Shor's Algorithm on a sufficiently capable quantum computer.

### PQC replacement

ML-KEM-768 provides a post-quantum key encapsulation mechanism based on module-lattice cryptography.

### Measured performance impact

The modeled workflow was defined as:

ECDH:
- KeyGen
- SharedSecret

ML-KEM:
- KeyGen
- Encapsulation
- Decapsulation

Measured results:

| Metric | ECDH | ML-KEM |
|---|---:|---:|
| Mean workflow time | 0.102 ms | 0.560 ms |
| Median workflow time | 0.097 ms | 0.508 ms |

This corresponds to approximately:

- **5.48× mean workflow overhead**
- **5.23× median workflow overhead**

At the individual-operation level, ML-KEM encapsulation was close to ECDH shared-secret generation, with a mean ratio of approximately 0.96×. ML-KEM decapsulation was approximately 2.58× the measured ECDH shared-secret time.

### Measured size impact

| Object | Classical | ML-KEM |
|---|---:|---:|
| Public key | 91 B | 1,184 B |
| Shared secret | 32 B | 32 B |
| Key-establishment ciphertext | — | 1,088 B |

The measured ML-KEM public key was approximately **13.01×** the ECDH public-key size. The ML-KEM ciphertext was 1,088 bytes.

The shared-secret size remained **32 bytes** for both ECDH and ML-KEM in the measured implementations.

### Migration considerations

Migration from ECDH to ML-KEM should therefore account for:

- Increased public-key storage requirements
- Increased protocol message sizes
- ML-KEM ciphertext transmission
- Increased modeled computational cost
- Compatibility with existing key-establishment protocols

## 4. ECDSA to ML-DSA Migration

### Classical mechanism

ECDSA P-256 provides digital signatures based on elliptic-curve cryptography and is vulnerable to Shor's Algorithm against its underlying discrete-logarithm security assumption.

### PQC replacement

ML-DSA-65 provides a post-quantum digital signature mechanism based on module-lattice cryptography.

### Measured performance impact

The modeled workflow was defined as:

ECDSA:
- KeyGen
- Signing
- Verification

ML-DSA:
- KeyGen
- Signing
- Verification

Measured results:

| Metric | ECDSA | ML-DSA |
|---|---:|---:|
| Mean workflow time | 0.162 ms | 2.103 ms |
| Median workflow time | 0.156 ms | 1.730 ms |

This corresponds to approximately:

- **12.95× mean workflow overhead**
- **11.09× median workflow overhead**

The largest individual difference occurred during signing:

- ECDSA signing: approximately **0.038 ms**
- ML-DSA signing: approximately **1.517 ms**
- Mean ratio: approximately **40×**

Verification showed a smaller difference:

- Mean ratio: approximately **2.77×**

### Measured size impact

| Object | ECDSA | ML-DSA |
|---|---:|---:|
| Signature | 72 B | 3,309 B |

The measured ML-DSA signature was approximately **45.96×** the ECDSA signature size, adding **3,237 bytes** per signature.

### Migration considerations

Migration from ECDSA to ML-DSA should therefore account for:

- Signer computational overhead
- Increased signature transmission size
- Increased signature storage requirements
- Certificate and protocol-size implications
- Systems generating large numbers of signatures

---

## 5. RSA Migration Considerations

RSA-2048 is also vulnerable to Shor's Algorithm because its security depends on integer factorization.

The project does not treat ML-KEM as a direct one-to-one replacement for every RSA operation. The appropriate PQC mechanism depends on the cryptographic function being performed.

For example:

- Key establishment / encryption-related functionality → ML-KEM
- Digital-signature functionality → ML-DSA

This function-based mapping is important because ML-KEM and ML-DSA provide different cryptographic services.

The measured RSA-2048 public key was 294 bytes, compared with:

- ML-KEM-768 public key: 1,184 bytes
- ML-DSA-65 public key: 1,952 bytes

These measurements demonstrate that migration can substantially change public-key storage and transmission requirements.

---

## 6. Migration Priority

Based on the measured results, migration planning should consider both quantum risk and operational impact.

### High-priority considerations

**ECDSA → ML-DSA**

The measured signature size increased from 72 bytes to 3,309 bytes, while the modeled workflow showed approximately 12.95× mean timing overhead.

Systems with:

- High signature volume
- Bandwidth constraints
- Large certificate chains
- Storage-sensitive environments

should evaluate these effects carefully.

**ECDH → ML-KEM**

The measured ML-KEM public key and ciphertext are substantially larger than the ECDH public-key representation. Protocols with constrained packet sizes or bandwidth should therefore be tested for compatibility and fragmentation effects.

---

### 6.1 Migration Decision Matrix

| Classical mechanism | Quantum risk | PQC replacement | Performance impact | Size impact | Migration priority |
|---|---|---|---|---|---|
| ECDSA-P256 | High — vulnerable to Shor's Algorithm | ML-DSA-65 | High; 12.95x modeled workflow overhead | Very high; 45.96x signature size | High |
| ECDH-P256 | High — vulnerable to Shor's Algorithm | ML-KEM-768 | Moderate; 5.48x modeled workflow overhead | High; ~13x public-key size and ~12x ciphertext reference size | High |
| RSA-2048 | High — vulnerable to Shor's Algorithm | Function-dependent: ML-KEM-768 / ML-DSA-65 | Operation-dependent | Public-key sizes increase relative to the measured RSA representation | High |
| AES-256 | Reduced security margin under Grover's Algorithm | Retain with adequate key size | No PQC migration required in this project | No public-key migration overhead | Monitor |
| HKDF-SHA256 | No direct Shor attack | Retain | No PQC migration required in this project | No public-key migration overhead | Maintain |

The migration priority reflects the combination of quantum vulnerability and the role of the mechanism in public-key cryptographic operations. The measured performance and size overheads describe implementation-level engineering considerations rather than reducing the underlying security priority of vulnerable classical mechanisms.

For RSA-2048, migration is function-dependent: ML-KEM is relevant to key establishment/encryption-related functionality, while ML-DSA is relevant to digital signatures.

## 7. Recommended Migration Approach

A practical migration process for quantum-vulnerable public-key cryptography is:

1. **Inventory**
   - Identify RSA, ECDSA, and ECDH usage across applications and infrastructure.

2. **Classify**
   - Determine whether each use case provides key establishment, encryption, authentication, or digital signatures.

3. **Assess quantum exposure**
   - Identify mechanisms whose security assumptions are vulnerable to Shor's Algorithm.

4. **Select PQC replacements**
   - Use ML-KEM for key establishment.
   - Use ML-DSA for digital signatures.

5. **Benchmark**
   - Measure computational cost, object sizes, bandwidth impact, and application-level latency.

6. **Test compatibility**
   - Evaluate protocol limits, certificate sizes, packet sizes, storage requirements, and implementation compatibility.

7. **Deploy using an appropriate transition strategy**
   - Where required, use hybrid classical/PQC mechanisms during migration while compatibility and interoperability are established.

8. **Retire vulnerable mechanisms**
   - Remove or reduce dependence on quantum-vulnerable public-key mechanisms once PQC deployment is sufficiently mature.

---

## 8. Overall Assessment

The experimental results demonstrate that post-quantum migration introduces measurable computational and communication overhead.

For the measured implementations:

- ECDH → ML-KEM showed **5.48×** modeled mean workflow overhead.
- ECDSA → ML-DSA showed **12.95×** modeled mean workflow overhead.
- ML-KEM public-key size was **13.01×** the measured ECDH public-key size.
- ML-DSA signature size was **45.96×** the measured ECDSA signature size.

These costs should be considered engineering trade-offs rather than reasons to avoid migration. The motivation for migration is that RSA and elliptic-curve mechanisms are vulnerable to sufficiently capable quantum computers, while ML-KEM and ML-DSA are designed to provide post-quantum security.

The results therefore support a migration strategy based on **cryptographic function, quantum risk, and measured operational constraints**, rather than a simple algorithm-for-algorithm replacement.
